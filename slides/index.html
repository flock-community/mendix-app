Migration approach

From Mendix to Next.js

How the TodoApp was rebuilt test-first, with the original's own theme and markup, and checked against the original on every push.

flock-community/mendix-app

The goal

Same app, new stack, and proof that it is the same

A Mendix 11 app (todos per user, a data grid with filters, a popup form, demo users) rebuilt as a Next.js app that behaves and looks the same, with parts that carry over to the next migration.

The original is the spec

One end-to-end suite runs against Mendix and the rebuild. What passes on one must pass on the other.

Reuse the original's look

Compile Mendix's own theme and render Mendix's own markup, instead of restyling by eye.

Built to repeat

The theme compiler and the component library are a package, not part of the app.

Mendix 11.16 Next.js 16 Playwright GitHub Actions

Step 1 · Read the model

Everything is in the project files

Mendix SQLite

Sources

  • TodoApp.mpr: a SQLite index of model units, stored as BSON in mprcontents/
  • 01-todo.mdl: the app written as an mxcli script
  • Theme SCSS: Atlas Core plus the mxcli “Signal” palette
  • Widget packages (.mpk): Data grid 2 3.4, Combo box 2.5, …

What came out

  • Layouts, pages and every widget with its properties
  • Navigation, roles, access rules and demo users
  • Widget defaults and DOM, read from the widgets' code
  • Exact texts from the system texts: “The username or password you entered is incorrect.”

Step 3 · Compile the theme

Same CSS, so the same pixels

Sass Bootstrap (Atlas) Node.js 
$ npx atlas-theme --project ../mendix --out public
atlas-theme: 5 theme sources, 7 widget packages,
             3 icon collections -> public

Runs before every next dev and next build, so the rebuild always wears the current Mendix theme.

What it writes

  • theme.compiled.css: dart-sass, in MxBuild's module order
  • widgets.css: the CSS inside the .mpk packages
  • mxicons/: icon fonts and classes, read from the .mpr
  • login.html: the theme's own page, placeholders filled in
  • Fonts, images and public resources, where Mendix serves them

Step 4 · In code

A page reads like its Mendix model

<LayoutGrid name="mainGrid">

      className="table-hover table-striped"

</LayoutGrid>

Renders what Mendix renders

<div class="mx-layoutgrid mx-layoutgrid-fluid
            mx-name-mainGrid">
  <h2 class="mx-name-heading mx-text">…
  <button class="btn mx-button
               mx-name-btnNew btn-primary">…
  <div class="mx-name-dgTodos table-hover
            table-striped widget-datagrid">…

The name becomes the mx-name-* class: Atlas styles it, and the e2e suite finds it in both apps.

The next migration

A playbook that carries over

  • Run atlas-theme on the Mendix project
  • Write the e2e suite against Mendix first, on mx-name-* selectors
  • Compose the pages from atlas-ui; port microflows and access rules to the server
  • Run both apps in CI and work through the screenshot diffs
  • Retire Mendix: commit the baselines and the theme output

Reusable as is

  • atlas-theme CLI (MPR v1 and v2 projects)
  • Core widgets, Data grid 2, filters, Combo box
  • useListValue + conditionToSql
  • The two-target Playwright setup and CI workflow

More widgets (gallery, tab container, …) as the next app needs them.
